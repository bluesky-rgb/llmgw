# 已实现部分的问题排查（2026-11-21）

范围：任务 0.1–1.3 已合并的全部代码（core、config、server、测试与 CI）。结论：发现 18 个问题，其中 16 个已修复、每个都有测试；1 个只修复了一部分；1 个降级为文档说明。另外记录 8 项暂时接受的风险。

## 方法

| 手段 | 内容 |
|---|---|
| 独立审查 | 一个没有参与实现的审查者，只拿到代码和设计文档，按“攻击者 / 慢客户端 / 坏上游 / 资源耗尽 / 文档与实现不一致”逐项检查 |
| 自查清单 | 竞速与取消语义、异常路径、超时分类、资源上限、日志中的敏感信息、测试是否真的测到目标 |
| 探测程序 | 手工构造的畸形 HTTP 请求（请求走私、非法字段名、裸 LF 等），确认 Beast 的实际行为而不是假设 |
| 模糊测试（新增） | 配置解析、语法解析、请求体字段提取三个入口；CI 中每次 60 秒 × 3 个目标（`tests/fuzz/`） |

规则：**每个问题先写一个能复现它的测试，确认失败，再修复**；关键的测试做反向验证（破坏修复，确认测试失败，再逐字节确认恢复）。

## 发现的问题

严重程度：🔴 可被远程利用或导致服务不可用；🟠 错误行为或资源泄漏；🟡 文档、可观测性或测试质量。

| # | 问题 | 程度 | 怎么修的 | 测试 |
|---|---|---|---|---|
| 1 | **没有写超时**：客户端只发请求不读响应，连接和流永远占着名额。`max_connections` 个这样的客户端就能让网关拒绝所有人 | 🔴 | 新增 `server.write_timeout`（默认 60 秒）。“超时”指**没有进展**：通过内核的 `SIOCOUTQ`（发送队列中未确认的字节数）判断客户端是否在读 | `client_that_never_reads…`、`stream_to_client_that_stopped_reading…` |

| 10 | 请求体中重复的 `model` / `stream`、对象后多余的内容被接受：网关按哪一个路由、上游按哪一个处理，可能不一致 | 🟠 | 重复键、多余内容 → 400 | `rejects_duplicate_keys…` |

## 暂时接受的风险

| 风险 | 为什么现在接受 | 什么时候解决 |
|---|---|---|
| 只关闭写方向（半关闭）的客户端被当作断开 | HTTP 客户端几乎不这样做；支持它会让断开检测复杂得多 | 有真实需求时 |
| 32 MB 请求体取字段约 8 ms，期间同一 Worker 上的连接要等 | 只读两个字段已经是 nlohmann 的 1/35；更大的请求体本来就少见 | 3.x：超大请求体交给 BlockingPool |
| 没有全局的“进行中的请求体总量”上限：`max_body_bytes` 最大可配 1 GB，并发大请求体可以耗尽内存 | 默认 32 MB × `max_connections`；需要按内存预算做准入控制 | 3.x |
| simdjson 的线程局部解析器保留最大一次请求体大小的内存 | 每个 Worker 最多 32 MB 级别，换来零分配 | 观察 1.2 的内存指标后决定 |
| 请求体中被跳过的嵌套值不做完整校验（`messages` 里的语法错误由上游报告） | 完整校验就是整体解析，回到 7.5 ms/MB | 1.6（协议转换时本来就要解析） |
| 配置文件中重复的键：后者覆盖前者，不报错 | nlohmann 的行为；配置文件由运维编写，风险低 | 1.1 的后续改进 |
| 不支持 `NO_PROXY`；代理认证在 1.4 | 1.4（上游连接）之前代理配置还不会被使用 | 1.4 |
| 活跃连接数、进行中的请求数还没有指标 | 指标模块在 1.2 | 1.2 |

## 收获与教训

1. **独立审查找到了自查漏掉的 11 个问题**，其中 3 个 🔴。自查时我检查的是“我设计的逻辑有没有错”，审查者检查的是“一个恶意或不正常的对端能做什么”。以后每个涉及网络输入的任务，验收都包括一次这样的独立审查
2. **库的语义要读文档、写测试确认，不能凭名字猜。** `a || b` 看起来是“谁先结束算谁”，实际是“谁先成功算谁”；Beast 的 `insert()` 看起来会校验，实际不校验。这两个假设分别导致了 #2 和 #3
3. **“超时”要定义清楚是在等谁。** 一个 `idle` 超时同时管“等上游”和“等客户端”，结果两头都错（#1、#6）。现在每个超时都对应一个具体的等待对象
4. **内核行为会让“显而易见”的实现失效。** 第一版写超时按 `async_write_some` 的完成来判断进展，但 Linux 只在发送缓冲区空出 1/3 时才唤醒写操作，慢速读取的客户端被误判为不读。最后用 `SIOCOUTQ` 直接看内核的发送队列
5. **模糊测试的成本很低，第一次运行就有收获**（#12）。所有解析外部输入的入口都应该有一个模糊测试目标
6. **修复本身也会引入 bug**（#17），以及**测试本身也会不稳定**（#18）。前者靠原有测试发现，后者靠在 sanitizer 下多次运行发现：修复之后要跑全部测试、在所有构建中各跑多次。**检查本身也要验证**：本机的格式检查用 grep 匹配 `warning`，而 clang-format 报的是 `error`，检查一直没有生效，直到 CI 失败才发现。现在按退出码判断，并确认它对未格式化的代码确实返回失败
7. **两阶段修改**：一次脚本里的多处替换，先检查每一处的原文都恰好出现一次，全部通过才写入。本次排查中它阻止了 1 次“只改了一半”的情况
