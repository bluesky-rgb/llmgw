## 1. 目标与范围

**一句话：** 让鉴权、限流、预算（2.2–2.4）可以作为插件接进 Session：配置中的 `pipeline` 决定启用哪些插件、按什么顺序；**只要某个插件的 `on_request` 被调用过，它的 `on_complete` 就一定会被调用恰好一次**，不论请求以什么方式结束。两个例外：`on_complete` 阶段超过 5 秒的限时（插件的缺陷）；进程退出时还在进行的请求。路线图的完成标准：`on_complete` 在所有终态下都会执行。

| 做 | 不做 |
|---|---|
| `Middleware`、`MiddlewareFactory` 接口；`Registry`（插件注册表）；`Chain`（每个 Worker 一条链） | 任何具体的插件（auth、ratelimit、budget 在 2.2–2.4） |
| 配置的 `pipeline` 部分：解析、校验（插件名拼错时给建议、列出可用的插件）；`llmgw check` 也校验 | 配置热加载时重建链（3.1） |
| Session 在 dispatch 之前执行 `on_request`、请求结束后执行 `on_complete`；拒绝时返回插件给出的错误 | 插件直接给出完整响应（缓存命中，v1.0 之后）：`Decision` 留出扩展的位置 |
| 插件可以给响应加响应头（2.3 的额度响应头需要） | `/v1/models` 是否经过中间件（2.2 决定） |
| 插件抛异常、`on_complete` 卡住时的隔离 | 优雅退出时等待进行中的请求（3.3） |
| `llmgw plugins`：列出二进制中注册的插件 | |

## 2. 在架构中的位置

- 模块：`middleware`（新代码）、`server`（Session 调用链）、`config`（`pipeline` 部分）、`app`（组装：注册内置插件、校验、为每个 Worker 建链）
- 依赖：`server → middleware` 已经在 `tools/module_deps.json` 中；middleware 只用到 `core`、`config`。**不新增依赖**
- Session 仍然是唯一的编排者：链不知道 router、executor 的存在；Dispatcher 不知道链的存在（dispatcher.h 中已经这样约定）

```
handle_chat:  ┌ relay ──────────────────────────────────┐ ‖ 客户端断开 ‖ 总截止时间
              │ chain.on_request → dispatch → respond   │
              └─────────────────────────────────────────┘
              竞速结束之后（不在竞速里，不会被取消）：chain.on_complete（限时 5 秒）
```

## 3. 接口设计

```cpp
// src/middleware/include/llmgw/middleware/middleware.h
namespace llmgw::middleware {

/// on_request 的结果：放行，或者拒绝（返回 error 对应的状态码）。两种情况都可以附加响应头。
struct Decision {
  std::optional<Error> reject;          ///< 有值：拒绝，之后的插件和 dispatch 都不执行
  std::vector<Header> response_headers; ///< 加到响应上（成功和拒绝都加），比如额度响应头
  static Decision pass();
  static Decision deny(Error error);
};

/// 每个 Worker 一个实例，只在该 Worker 的线程上调用，不需要加锁。
class Middleware {
 public:
  virtual ~Middleware() = default;
  [[nodiscard]] virtual Task<Decision> on_request(RequestContext* ctx) = 0;
  /// 只要 on_request 被调用过（包括它抛了异常、请求被它或后面的插件拒绝），就一定会被调用一次；
  /// 终态在 ctx->outcome。不会被客户端断开取消；不能等待没有上限的外部 I/O（整个阶段限时 5 秒）
  [[nodiscard]] virtual Task<> on_complete(const RequestContext* ctx) = 0;
};

/// 一个插件在配置中的设置。config_json 是 pipeline 中这一项的 "config" 对象的 JSON 文本
/// （没有写时为 "{}"）；path 是它在配置文件中的位置（错误提示用）。
struct PluginSpec { std::string name; std::string config_json; std::string path; };

/// Worker 级的资源，传给 create()。
struct WorkerResources {
  unsigned index = 0;
  unsigned worker_count = 1;
  boost::asio::any_io_executor executor;
  MetricsRecorder* metrics = nullptr;
};

/// 插件工厂：全局一个、只读，可以被所有 Worker 同时调用 create()。
class MiddlewareFactory {
 public:
  virtual ~MiddlewareFactory() = default;
  [[nodiscard]] virtual std::string_view name() const = 0;
  [[nodiscard]] virtual std::string_view description() const = 0;
  /// 校验插件的配置。返回的问题会和配置文件的其他问题一起报告（llmgw check、启动时）
  [[nodiscard]] virtual std::vector<config::Issue> validate(const PluginSpec& spec,
                                                            const config::Snapshot& snapshot) const = 0;
  /// validate 通过之后才会调用。
  [[nodiscard]] virtual std::unique_ptr<Middleware> create(const PluginSpec& spec,
                                                           const config::Snapshot& snapshot,
                                                           const WorkerResources& worker) const = 0;
};
}
```

```cpp
// registry.h
class Registry {            // 启动时填好，之后只读；所有 Worker 共享
 public:
  Result<void> add(std::unique_ptr<MiddlewareFactory> factory);  // 重名 → 错误
  [[nodiscard]] const MiddlewareFactory* find(std::string_view name) const;
  [[nodiscard]] std::vector<const MiddlewareFactory*> all() const;  // 按名字排序
};
/// 校验 snapshot.pipeline：插件名存在（拼错时给建议、列出可用的插件）、不重复、各插件的 validate
[[nodiscard]] std::vector<config::Issue> validate_pipeline(const config::Snapshot&, const Registry&);

// chain.h
class Chain {               // 每个 Worker 一条，按 pipeline 的顺序
 public:
  static Result<std::unique_ptr<Chain>> build(const config::Snapshot&, const Registry&,
                                              const WorkerResources&);
  [[nodiscard]] bool empty() const;
  /// 一个请求在链上的进度：on_request 执行到了第几个插件。放在 Session 的栈帧中
  struct Run { std::size_t entered = 0; std::vector<Header> response_headers; };
  /// 依次执行；遇到拒绝就停下。插件抛异常 → 500（kInternal），也算 entered
  [[nodiscard]] Task<Decision> on_request(RequestContext* ctx, Run* run);
  /// 按相反的顺序，对 entered 个插件执行 on_complete；某个插件抛异常时记录下来，继续执行其余的
  [[nodiscard]] Task<> on_complete(const RequestContext* ctx, const Run* run);
};
```

`config::Snapshot` 增加 `std::vector<PipelineEntry> pipeline`（`name`、`config_json`、`path`）；`server::ServerOptions` 增加可选的 `ChainFactory`（与 `DispatcherFactory` 一样，为每个 Worker 创建一条链）。

## 4. 数据与状态

| 数据 | 归属 | 线程 |
|---|---|---|
| `Registry` 及其中的工厂 | app 在 `main` 中创建，生命周期覆盖整个进程 | 全局只读 |
| `Chain` 及其中的插件实例 | Worker（与 Dispatcher 一样，先于 io_context 销毁） | 单个 Worker |
| `Chain::Run` | handle_chat 的栈帧（与 `RequestContext` 并列） | 请求级 |
| 插件附加的响应头 | `Run::response_headers` | 请求级 |

## 5. 关键流程

1. `handle_chat` 创建 `RequestContext` 和 `Chain::Run`
2. 竞速中的 `relay`：`chain.on_request(ctx, &run)`
   - 拒绝：`outcome = kRejected`，写插件给的错误（加上附加的响应头），不调用 dispatch
   - 放行：dispatch → respond，响应头中加上附加的响应头
3. 竞速结束（不论哪个分支赢）之后、`handle_chat` 返回之前：`chain.on_complete(ctx, &run)`。这里不在竞速中，客户端断开、总超时都不会取消它
4. 管道为空时，第 2、3 步什么都不做（不建定时器，热路径没有额外开销）

## 6. 失败与边界情况

| 情况 | 处理 |
|---|---|
| 插件名不存在 / 拼错 | 配置错误：“没有名为 xxx 的插件（是不是 yyy？）；可用的插件：…”。启动失败 |
| 同一个插件出现两次 | 配置错误（执行顺序和计数会有歧义） |
| `pipeline` 中的项既不是字符串也不是对象、`config` 不是对象、有未知字段 | 配置错误，指出路径 |
| 插件的 `on_request` 抛异常 | 这个请求返回 500；它和之前的插件都会收到 `on_complete`；记录日志和指标 |
| `on_request` 期间客户端断开 / 总超时 | 竞速取消 `on_request`；已进入的插件（包括被取消的那个）都会收到 `on_complete`，`outcome` 是 kClientAborted / kTimeout |
| 插件的 `on_complete` 抛异常 | 记录日志和指标，继续执行其余插件的 `on_complete`（stability.md 第 5 节） |
| `on_complete` 卡住 | 整个阶段限时 5 秒：超时后取消，剩下的插件不再执行，记录日志和指标，关闭连接。这是插件的缺陷（违反接口约定），不能让它永远占住一个连接名额 |
| 竞速的分支不能抛异常（relay.cpp 的规则） | `on_request` 的异常在 `relay` 中捕获 |
| Worker 停止（进程退出）时还在进行的请求 | 协程帧被直接销毁，`on_complete` **不会**执行。如实写进接口说明；预算（2.4）的冻结额要有过期机制，优雅退出（3.3）会先等进行中的请求结束 |
| 解析请求体失败（400）、路径不存在（404）、方法不对（405） | 发生在建立 `RequestContext` 之前，不经过链，也就没有 `on_complete` |

## 8. 风险与备选方案

| 问题 | 选择 | 备选与理由 |
|---|---|---|
| 插件怎样注册 | **显式注册**：`middleware::register_builtin(Registry*)` 列出内置插件，app 在 main 中调用 | extensibility.md 原来写的是 `LLMGW_REGISTER_MIDDLEWARE` 宏（静态初始化时自动登记）。插件放在静态库里，没有被引用的目标文件会被链接器丢掉，宏就悄悄失效；还有静态初始化顺序问题、全局可变状态（与 PR 检查清单冲突）。显式列表多一行代码，换来确定性。记为 ADR-009，同步修改 extensibility.md |
| 插件配置的类型 | JSON 文本 + 配置文件中的路径 | 把 config 内部的 nlohmann 类型暴露到公开头文件，违反 code-architecture.md 3.7；自己定义一套 JSON 值类型，工作量大且重复。插件在自己的 .cpp 中解析（只在启动时） |
| `on_request` 放在竞速里面还是外面 | 里面 | 鉴权、限流可能等待（比如访问 Redis），客户端断开时应当取消；放在外面就没法取消 |
| `on_complete` 要不要限时 | 整个阶段限时 5 秒，超时关闭连接 | 不限时：一个有缺陷的插件可以永远占住连接名额。每个插件单独限时：每个请求每个插件一个定时器，热路径的开销；而且卡住本来就是缺陷 |
| `Run` 放在哪里 | Session 的栈帧 | 放进 `RequestContext`：core 就要知道中间件链，违反依赖方向 |
