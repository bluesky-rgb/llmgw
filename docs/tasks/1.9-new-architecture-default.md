## 1. 目标与范围

**一句话：** 证明新架构（1.1–1.7）能做原型能做的事，并且更快、更省；然后让它成为用户拿到的默认程序，原型只作为压测的对照组。**路线图的验收标准：原型的端到端测试在新架构上全部通过；压测报告 #1；新架构成为默认。**

**要做：**

| 部分 | 内容 |
|---|---|
| 测试迁移 | 原型 `prototype/tests/test_main.cpp` 的 13 个端到端测试，逐个写成新架构的测试（进程内 Server + Gateway + 测试上游）。**有意改变的行为**不照搬原型，而是测试新的行为，并在下表中说明理由；推迟到后续任务的功能（鉴权、指标）标明任务号 |
| 安全的默认值 | 新架构在 2.2 之前没有客户端鉴权。`llmgw serve` 在数据面监听**非本机地址**时拒绝启动，除非加 `--allow-unauthenticated`（见第 3 节） |
| 压测报告 #1 | 按 benchmark.md 的方法（分核、同一套场景）测新架构：B1 并发与内存、B2 额外延迟、B3 与原型对比、B5 每块 CPU。与 0.7 的 demo 对比，解释差异 |

## 3. 没有鉴权时的保护

**风险：** 新架构持有作者的上游 key，却不检查客户端是谁。数据面默认监听 `0.0.0.0`（为了容器部署）。如果 1.9 之后用户照着 README 在服务器或 Docker 里启动，任何能访问这个端口的人都能用作者的 key 调用模型，产生费用。原型有 `api_keys`，所以这对用户来说是**退步**。

**做法：** `serve` 启动时检查数据面的监听地址。不是本机地址（`127.0.0.0/8`、`::1`、`localhost`）时，拒绝启动（退出码 1），提示“2.2 之前网关不做鉴权；只在本机使用，或者确认网络可信后加 `--allow-unauthenticated`”。加了这个参数时，启动后在标准错误中打印警告。2.2 实现鉴权后改为：配置了 `keys` 就正常启动，没有配置时仍然要求这个参数。

| 备选 | 为什么不选 |
|---|---|
| 把默认地址改成 `127.0.0.1` | 容器中必须监听 `0.0.0.0`，用户会直接改配置，保护就没有了；而且改的是配置的默认值，影响 2.2 之后的行为 |
| 只打印警告 | 后台运行时没有人看标准错误 |

## 4. 压测

方法与 0.7 完全相同（benchmark.md“环境与方法”），被测程序换成 `build/src/app/llmgw serve`（Release，`workers: 1`）。负载 B1 5000 / 9000 条流、B2 1000 条流 × 100 块、B3 与原型、B5 每块 CPU。

**预期与需要解释的差异：** 新架构每个请求比 demo 多做的事：请求体改写（simdjson）、SSE 解析与用量提取、连接池、看门狗、竞速。TTFB 应该比 demo **更低**（连接池复用上游连接），每块 CPU 可能略高（SSE 解析）。如果每块 CPU 比 demo 高出 50% 以上，先定位原因再出报告。

## 收获与教训

1. **压测不只是出数字**：设计中“比 demo 高 50% 就先定位”的规则直接找到了一个 1.4 留下的问题。`resize` 出 16 KB 再缩回去，在每个单元测试里都正确，只有按“每块数据”统计时才看得出来：一百多字节的数据要清零 40 KB。性能问题要用性能工具（callgrind）找，读代码时很难注意到
2. **指令数和 CPU 时间不是一回事**：去掉 memset 后指令数少了 57%，CPU 时间只少了一点（AVX2 清零很快）；真正省下的是内存（每条流 40 → 28 KB）。报告里两个数字都要给
3. **安全判断要基于系统实际使用的值**：按字符串判断“是不是本机地址”，和系统按解析结果绑定之间有差异，审查者用 hosts 文件就绕过了。凡是“检查之后再使用”的地方，检查的必须是将要使用的那个值
4. **核对文档时会发现之前的错误结论**：1.7 的风险表写“网关的 504 会被 SDK 重试”，是没有查代码就写的推断；这次查代码时发现网关的错误早就带 `x-should-retry`，真正的缺口在另一处（原样转发的上游 500）。结论都要以代码或测试为依据
5. **压测期间不能做别的事**：机器只有 2 个核，压测时编译或跑测试会直接污染数据。这次把等待时间用来写文档
