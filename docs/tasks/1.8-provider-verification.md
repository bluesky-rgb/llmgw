## 1. 目标与范围

**一句话：** 用作者手上的真实 key，把 providers.md 验证清单的 12 项逐项填完；把真实的响应录下来，作为回归测试的数据。**路线图的验收标准：清单 12 项填完；样本加入回归测试。**

这个任务分成两半：

| 部分 | 谁来做 | 在哪里 |
|---|---|---|
| 探测工具 `tools/provider-probe/probe.py`：直连三家上游 + 经过 `llmgw serve`，输出报告和样本 | Claude（这里） | 仓库；`--self-test` 用假上游完整跑一遍，在 CI 中运行 |
| 运行探测工具 | **作者**（只有作者的电脑上有 key） | 作者的电脑：`export` 三个 key，运行一条命令 |
| 根据报告更新 providers.md、配置示例、`error_mapping`；样本加入回归测试 | Claude | 仓库 |

**密钥的规则（项目的硬性要求）：** key 只在作者电脑的环境变量中。探测工具只从环境变量读取 key；写任何文件之前，检查内容中没有任何一个 key（出现就中止，不写文件）；请求头、响应头都不写进样本；网关的临时配置只写环境变量的名字（`api_key_env`）。

**要做：**
- `probe.py`（只用 Python 标准库，作者的电脑上不需要装任何东西）：
  - 清单的第 1–9、11、10 项自动完成；第 5 项（触发限流）会产生一串请求，默认不做，`--burst N` 才做
  - 第 12 项（账号的实际配额）只能在各家的控制台看到：报告中留出表格，由作者填写
  - `--gateway <llmgw 可执行文件>`：用同样的环境变量生成临时配置，启动 `llmgw serve`，经过网关再测一遍（基本调用、usage 块的处理、401 时切换到下一个目标）。这是 1.7 的 `serve` 第一次接真实上游
  - 输出目录：`report.md`（给人看的结论）、`report.json`（完整数据）、`samples/<上游>/*.sse|*.json`（去掉敏感内容的响应体）
- `--self-test`：启动一个模拟三家行为的假上游（包括 MiniMax 风格的 `base_resp`），完整运行一遍，检查报告的每一项都有结果、密钥检查有效（故意把假 key 放进响应体，必须中止）。加入 ctest
- 回归测试的框架：`tests/data/providers/<上游>/*.sse` 中的每个样本都经过 1.5 的 `stream::open()`，检查不变式（每个事件都被解析、`[DONE]` 之后没有数据、usage 被提取、去掉 usage 块后其余内容不变）。没有样本时这个测试显示“跳过”而不是“通过”

**不做：**
- 任何需要在 CI 中使用真实 key 的测试（会产生费用、key 不能进 CI）
- 根据结果修改网关的代码：如果结果与 providers.md 的假设不符（比如 MiniMax 出错时 HTTP 状态码就是对的），在本任务中只更新文档和配置示例，代码的改动另开任务（路线图第 6.1 节）

## 2. 探测内容

每家上游默认约 20 个请求（`max_completion_tokens` 都很小），`--burst` 另算。MiMo 的 Token Plan 按额度限量，这个量级可以忽略。

| 清单 # | 方法 | 记录 |
|---|---|---|
| 1 | 非流式、流式各一次，提示词让模型只回答一个字 | 状态码、耗时、回答是否非空、`finish_reason` |
| 2 | 流式 + `stream_options.include_usage = true`；再来一次不带 | 是否有 usage 块、它是不是最后一个事件、不带时是否仍然返回 |
| 3 | 同上的 usage 中是否有 `completion_tokens_details.reasoning_tokens`；是否有 `reasoning_content` 字段 | 字段的路径和值 |
| 4 | 用一个无效的 key（`sk-llmgw-probe-invalid`）各发一次非流式、流式 | HTTP 状态码、响应体（作为样本）、是否有 `base_resp`。**MiniMax：确认出错时 HTTP 状态码是不是 200**（providers.md 3.4） |
| 5 | `--burst N`：同时发 N 个最小的请求 | 第一次出现 429 的位置、`Retry-After`、响应体 |
| 6 | 分别带上：历史消息中的 `reasoning_content`、顶层的 `thinking`、`reasoning_split` | 每种的状态码；400 时的错误信息 |
| 7 | 分别用 `max_tokens`、`max_completion_tokens` | 状态码、是否生效（输出 token 数） |
| 8 | 流式请求 5 次，默认推理强度 | 首字延迟（第一个带内容的事件，包括 `reasoning_content`）的中位数、最大值；首个事件的延迟 |
| 9 | 一次请求之后保持连接，每 5 秒检查一次服务端是否关闭了连接，最多 `--idle-max` 秒（默认 180） | 关闭的时刻（或“超过 180 秒仍未关闭”）。经过代理时测到的是隧道，同样能反映上游 |
| 11 | 所有响应头中名字含 `ratelimit`、`quota`、`remaining`、`limit` 的项 | 名字和值 |
| 10 | 第 1、2、4、6 项的响应体 | `samples/` 中的文件；`id`、`created` 等字段替换为固定值 |

经过网关（`--gateway`）：每家上游一个只有它自己的模型，各发一次非流式、流式（不带 `include_usage`：客户端不应该看到 usage 块；带：应该看到）；一个“先无效 key、再真实上游”的模型：应该成功，`X-LLMGW-Attempts: 2`。

## 3. 失败与边界情况

| 情况 | 处理 |
|---|---|
| 某个 key 没有设置 | 跳过这家上游，报告中注明 |
| 网络不通、需要代理 | 直连部分使用 `HTTPS_PROXY` 等环境变量（urllib 的默认行为）；网关部分用配置的 `proxy`（生成临时配置时从同样的环境变量读取） |
| 模型名不对 | 默认值来自 providers.md，可以用 `OPENAI_MODEL` 等环境变量覆盖；404 时报告中提示 |
| 某一项失败（超时、异常） | 记录为“出错”和原因，继续下一项，不中止整个探测 |
| 响应中出现 key（比如上游在错误信息里回显了 key 的一部分） | 写文件之前检查；出现完整的 key 就中止，并提示作者；只出现前几位时替换为 `***` |
| 作者中途按 Ctrl-C | 已经完成的部分写入报告 |
