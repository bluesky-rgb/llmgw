## 1. 目标与范围

**一句话：** 用最少的代码，验证 v1.0 并发方案中**风险最大的几件事**能不能用 Asio + Beast + C++20 协程做出来，并且做得够好。结果决定关口 G1：继续用 Asio，还是换成 Drogon。

**要验证的 5 件事：**

| # | 要验证什么 | 为什么有风险 |
|---|---|---|
| 1 | 每核一个线程 + `SO_REUSEPORT` + 每条连接一个协程 | 整个并发模型的基础 |
| 2 | Session 的“拉取循环”：读上游一块、写客户端一块 | 背压是否真的自然成立 |
| 3 | **客户端断开后，立即取消上游请求**（不等到下一块数据） | 原型做不到；这是“不多花钱”的关键 |
| 4 | 总超时：超时立即结束，并取消上游请求 | 需要用 `||` 让多个等待操作“竞速” |
| 5 | 上万条并发流时的内存和 CPU | 产品定位的第二卖点 |

**不做：** 连接池、TLS、鉴权、路由、重试、配置文件、指标体系等。这些都在阶段 1 的正式代码中实现。**demo 的代码不会直接进入 `src/`**，只用来验证和学习；正式实现时按 `src/` 的规范重写。

## 2. 在架构中的位置

- 位置：`spike/coroutine-proxy/`，不受 `src/` 的模块规则约束；默认不参与构建（`LLMGW_BUILD_SPIKE=OFF`），避免 CI 每次都下载 Boost
- 新增依赖：**Boost 1.92.0**（只使用 Asio 和 Beast，都是纯头文件库）

### 3.2 Session 的核心循环

> ⚠️ **设计变更（2026-11-20，验证中发现）**：下面的“原设计”在每个数据块上都做一次竞速，实测开销过大，已改为“每个请求只竞速一次”。原因和数据见验证记录 D2。

**现设计：**

```cpp
awaitable<bool> Session::relay(...) {
  connect_and_send();                                      // 只和截止时间竞速
  // 一个请求只竞速一次：拉取循环 / 客户端断开 / 总超时 / 空闲超时
  auto r = co_await (pump() || client_closed() || deadline() || idle_watch());
  // r.index() 说明是谁先结束的；其余三个已被 Asio 自动取消
}
awaitable<PumpResult> Session::pump() {
  read_header(); write_header_to_client();
  while (!done) {
    parse_buffered_data_into_16KB_chunk();                  // 缓冲区里已有的分块先解析，凑满再写
    if (chunk_ready) co_await write_client_chunk();         // 写完才读下一块：背压
    if (need_more)   co_await read_upstream_some();         // 缓冲区空了才读上游
  }
}
```

- **空闲超时用“惰性定时器”**：数据到达时只记录时间，不重设定时器；定时器到期时如果期间有过活动，就顺延
- 竞速的各个分支引用 relay() 栈帧里的状态；relay() 等竞速结束才返回，所以引用一直有效

**原设计（已废弃）：**

```cpp
awaitable<void> Session::proxy_stream(...) {
  for (;;) {
    // 三者竞速：上游的下一块数据 / 客户端断开 / 总截止时间
    auto r = co_await (read_upstream_chunk() || client_closed() || deadline());
    if (r.index() != 0) { cancel_upstream(); co_return; }   // 客户端走了或超时：立即取消上游
    if (chunk.empty()) break;                                // 上游结束
    co_await write_client_chunk(chunk);                      // 写完才读下一块：背压
  }
}
```

- **竞速**：用 Asio 的 awaitable operators（`||`）。先完成的那个决定结果，其他的被自动取消
- **检测客户端断开**：在拉取循环期间，同时在客户端连接上等待“可读”。HTTP/1.1 中，客户端在等待响应时不会再发数据，一旦可读，通常意味着连接被关闭
- **背压**：只有写给客户端完成后才读上游的下一块；读写缓冲区都有固定上限

## 5. 失败与边界情况

| 情况 | 处理方式 | 对应的验证 |
|---|---|---|
| 客户端在等待上游时断开 | 竞速中“客户端断开”胜出 → 立即关闭上游连接 | D3 |
| 上游一直不发数据 | 空闲超时或总超时胜出 → 返回 504（还没发响应头时）或直接关闭 | D4 |
| 客户端读得很慢 | 写客户端阻塞，不读上游；内存不增长 | D2 |
| 上游连接失败 | 返回 502 | D1 |
| 请求头、请求体过大 | Beast 解析器的上限：请求体 32 MB | D1 |

## 6. 验证计划

| # | 验证项 | 方法 | 验收标准 |
|---|---|---|---|
| D1 | 功能正确 | 经 demo 访问 mock：非流式、流式、上游 503、上游不可达、连续两个请求复用连接（Keep-Alive） | 结果与直连 mock 一致；不可达时返回 502 |
| D2 | 背压 | 上游快速发送大量数据（mock `chunks=2000,interval=0`），客户端限速读取（`curl --limit-rate`） | demo 内存不随时间增长；上游的发送被拖慢（mock 统计中流的持续时间变长） |
| D3 | **客户端断开 → 立即取消上游** | 上游在第 1 块后卡住（`stall_after=1`），客户端 1 秒后断开；**同样的场景对比原型** | demo：mock 在客户端断开后 **100 毫秒内**统计到取消；原型：要等到读取超时 |
| D4 | 总超时 | 上游黑洞，`--total-timeout 2s` | 约 2 秒时客户端收到 504，mock 统计到取消 |
| D5 | 并发与内存 | 用 0.5 的 `loadcheck` 打开 5000 条流（每条 20 块、间隔 50 毫秒）；对比原型 | 全部成功；**每条流的内存 ≤ 100 KB**；记录 CPU 占用和额外延迟 |
| D6 | 内存与线程安全 | ASan + UBSan、TSan 构建下重复 D1、D3、D4 | 没有报错 |

**关口 G1 的判断标准（来自 roadmap）：** D5 支撑 5000 条以上的并发流、每条流内存不超过 100 KB，并且 demo 的代码能读懂、能讲清楚 → 继续用 Asio；否则评估 Drogon。

## 7. 风险与备选方案

| 风险 | 应对 |
|---|---|
| Beast 的流式读取（`buffer_body`）用法复杂 | 先做非流式，再做流式；参考 Beast 官方的 relay 示例 |
| 竞速取消后的对象生命周期问题 | 所有资源由协程栈持有；用 ASan 验证（D6） |
| 2 核机器上三个进程（mock、demo、客户端）争抢 CPU | 按 0.5 的经验，以 mock 服务端的发送偏差判断瓶颈；必要时用 `taskset` 分核 |

### D2：背压，以及一次设计变更

**第一个问题：`curl --limit-rate` 不能用来测背压。** curl 按平均速率限速：开始时一口气读走约 2.5 MB（各级 socket 缓冲区里的数据），然后长时间休眠，把平均速率拉回到设定值。看上去像代理“卡住了”，其实是测量工具的行为。改用 `verify/slow_reader.py`（接收缓冲区 16 KB，每 50 ms 读固定的量）。

**第二个问题（更重要）：原设计每块都竞速，开销是搬数据本身的 8 倍以上。** 同一次全速转发（9.6 MB，50000 个 SSE 事件）：

| 版本 | 全速转发 9.6 MB | 转发 5000 块的系统调用 |
|---|---|---|
| 直连 mock | 0.08–0.30 s | — |
| 原设计：每块竞速一次 | **2.44 s**（demo 单核 100%） | 112,732 次（`epoll_wait` 61,349、`timerfd_settime` 30,673、`sendmsg` 6,890） |
| 改为每请求竞速一次 + 惰性空闲定时器 | 0.12 s | 5,065 次 + 5,138 次 |
| 再加上“缓冲区里的分块凑满 16 KB 再写” | 0.14 s | **约 880 次**（`recvfrom` 219、`sendmsg` 208、`epoll_wait` 423） |

原因：`a || b || c` 每次都要启动三个异步操作，结束后再取消其中两个。两个定时器每次都要重设，客户端的“可读”等待每次都要重新注册到 epoll。数据块只有约 200 字节时，这些固定开销远大于搬数据本身。

**结论写入正式设计：** 竞速放在“一个请求”这个粒度上，而不是“一个数据块”；“一直在变”的超时用惰性定时器。这条要进入 Session 的模块设计（阶段 1）。

### D3：取消上游的时延

| 断开时机 | 直连 mock | 协程 demo | 原型 v0.1 |
|---|---|---|---|
| 流式输出中途（每 100 ms 一块） | 0.6 ms | **0.6 ms**（最大 1.0） | 203 ms（要等下一次写客户端失败） |
| 收到响应头、首字之前（`ttft`） | 0.5 ms | **0.6 ms** | **不取消**：上游把整段生成跑完（mock 计为“完成”而非“取消”） |
| 什么都没收到（`header_delay`） | 0.9 ms | **0.9 ms**（最大 3.8） | — |

测法：客户端读到指定内容后关闭连接，每 2 ms 轮询一次 mock 的 `streams_cancelled`。原型“首字前断开”的情况，客户端断开 7 秒后，mock 的 `streams_completed` 加 1、`streams_cancelled` 不变。**换成真实上游，这就是白白被计费的一整段生成。** 这是协程方案相对原型最重要的一项改进。

和设计的差异：设计写的是 `stall_after=1` + 1 秒后断开；实际用了三种断开时机，覆盖得更全。

### D5：并发与内存

5000 条流，每条 100 块、间隔 100 ms（每条约 10 秒），4 秒内逐步建立：

| 指标 | 直连 mock（基线） | 经过 demo |
|---|---|---|
| 成功 | 5000 / 5000 | 5000 / 5000 |
| 同时在线会话 | — | 5002 |
| demo 内存 | — | 空载 4.1 MB → 峰值 189.6 MB，**约 37 KB/流** |
| demo CPU | — | 7.6 s（14.7 s 内转发约 50 万块；约占 2 核的 26%） |
| 块间隔偏差 p50 / p99 | 0.76 ms / 45.5 ms | 6.2 ms / 100 ms |
| mock 自己测得的发送偏差 p99 | ≤ 20 ms | ≤ 50 ms |

**p99 变差的原因是同机 CPU 争抢，不是 demo 本身。** 证据：① mock 自己的发送偏差也从 ≤20 ms 升到 ≤50 ms，说明 mock 也在被饿着；② 降到 1000 条流、CPU 不饱和时，两次测试 demo 和直连几乎一样：

| 1000 条流 | p50 | p99 |
|---|---|---|
| 直连 mock | 0.69–0.71 ms | 1.65–1.71 ms |
| 经过 demo | 0.68 ms | 2.15–2.95 ms |

即 demo 额外增加的 p99 约 0.5–1.3 ms。**5000 流下的延迟结论留给 0.7，在分核或分机的环境里测。**

37 KB/流的构成（估算）：16 KB 的转发块 + 上游读缓冲区约 16 KB + 解析器、协程栈帧、请求缓冲区。阶段 1 可以按 Worker 复用转发块，进一步降低，但已经低于目标，不是现在的优先事项。

另外确认了**没有会话泄漏**：2000 条流结束后 0.5 秒内，会话数回到 1（只剩查询统计的那一条）；50 次中途断开后，mock 侧没有残留的活跃流。

D5 设计中要求“对比原型”，没有做：原型是每连接一个线程（配置 64 个线程），且需要鉴权和模型映射，`loadcheck` 不能直接用。它的并发上限就是线程数，这在设计上已经明确，不需要再测。

### 依赖安全检查（CI security 任务）

首次推送时，CI 的漏洞检查拦下了 Boost 1.92.0 的一个已知漏洞 **OSV-2024-112**：Boost.Graph 的 `read_graphviz` 解析子图时递归导致栈溢出（OSS-Fuzz 报告）。OSV 按整个 Boost 仓库的 commit 匹配，所以只要用 Boost 就会被报出来。

核对结果：参与构建的 50 个 Boost 库中**没有 graph**；demo 编译时实际包含的头文件中**没有 `boost/graph`**；本项目也不解析 Graphviz 文件。因此登记到 `tools/vuln_allowlist.json`，写明前提条件（`libraries` 中不包含 graph），失效日期 2027-05-20，到期自动重新报警。

这说明 0.1–0.3 建立的漏洞检查在新增依赖时确实起作用了。

## 收获与教训

1. **“看上去正确”的设计，要用系统调用的数量去检验。** 原设计的伪代码非常清楚，功能也完全正确，但每块都竞速让吞吐慢了 20 倍。`strace -c` 两分钟就定位到原因。以后涉及“每个数据块都要做的事”，都要先估算一次它的系统调用次数。
2. **测量工具本身要先验证。** `curl --limit-rate` 让背压测试看上去失败了，其实是 curl 的限速方式造成的。测量结果“不合理”时，先怀疑测量方法。
3. **对比实验比单独的数字更有说服力。** “取消时延 0.6 ms”本身不说明什么；和原型对比才看得出来：原型在首字前断开时根本不取消，上游的生成会被完整计费。这一条以后可以直接写进 README，作为产品的卖点。
4. **同机压测只能比较相对值。** 2 核机器上三个进程互相抢 CPU，绝对延迟不可信。必须同时记录基线（直连）和 mock 自己测得的偏差，才能判断瓶颈在哪里。
5. **验证脚本要进仓库。** 一开始脚本放在 `/tmp`，路径写死、有一处 JSON 引号还写错了；放进 `verify/` 并重新跑通之后，数字才可以被别人复现。
