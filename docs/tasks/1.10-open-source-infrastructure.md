## 1. 目标与范围

**一句话：** 让一个第一次看到这个仓库的人，能看懂它是什么、能跑起来、知道去哪里提问、知道怎样提交贡献、知道怎样私下报告安全问题；打 tag 时自动发布二进制和镜像。**路线图的验收标准：陌生人能看懂项目、能提问、能贡献。**

| 内容 | 做法 |
|---|---|
| `README.en.md` | 英文版：定位、三大支柱、当前状态（v0.2 Alpha 没有鉴权）、5 分钟上手、文档链接（文档本身是中文，注明）。`README.md` 顶部互相链接 |
| `CONTRIBUTING.md` | 开发环境、构建与测试、开发流程（任务设计 → 评审 → 实现 → 验证）、编码规范、提交规范、DCO |
| `CODE_OF_CONDUCT.md` | 采用 Contributor Covenant 2.1（引用原文链接，不复制全文），加上本项目的执行方式和举报渠道 |
| `SECURITY.md` | 支持的版本、私下报告的方式（GitHub 的私密漏洞报告）、响应时间承诺、范围（什么算安全问题） |
| Issue 模板 | `bug_report.yml`、`feature_request.yml`（表单）；`config.yml`：使用问题引导到 Discussions，禁止空白 Issue；保留维护者用的 `task.md` |
| Discussions | 开启（仓库设置）；问答和功能讨论放在这里 |
| 私密漏洞报告 | 开启（仓库设置），`SECURITY.md` 指向它 |
| DCO | CI 中的 `dco` 任务：**来自 fork 的 PR**，每个提交都要有 `Signed-off-by` |
| 自动发布 | `.github/workflows/release.yml`：推送 `v*` tag 时构建 Linux x86_64 二进制（tar.gz + SHA-256）、创建 GitHub Release，镜像推送到 `ghcr.io/bluesky-rgb/llmgw`；`workflow_dispatch` 可以只构建、不发布（验证用） |

**不做：** CHANGELOG（4.3）；更多平台的二进制（arm64、静态链接）；发布 v0.2 本身（关口 G2，等 1.8 完成）。

## 2. 决定

| 问题 | 决定 | 理由 |
|---|---|---|
| DCO 检查谁 | 只检查**来自 fork 的 PR** | 本仓库的提交由 AI 助手生成（git 身份 `Claude <noreply@anthropic.com>`），由它声明 DCO 没有意义；用作者的名义声明又是替作者做法律声明。维护者的提交本身就以 Apache 2.0 发布。CONTRIBUTING 中如实说明 |
| 行为准则的举报渠道 | GitHub 的私密报告（与安全问题相同的入口），注明“行为准则” | 不需要公开个人邮箱；以后作者提供专门的邮箱时替换 |
| 行为准则的正文 | 引用 Contributor Covenant 2.1 的官方页面 | 标准、被广泛认可；全文以链接为准，避免复制出错 |
| 二进制的构建环境 | 与镜像相同（Ubuntu 24.04 的构建阶段），从镜像中取出 | 一处构建、二进制与镜像完全一致；需要 glibc 2.39、OpenSSL 3，发布说明中写明 |
| 安全响应时间 | 7 天内确认收到，30 天内给出修复或缓解方案 | 维护者只有一人；承诺做不到比不承诺更糟 |
| 第三方许可证（评审后增加） | `tools/third_party_licenses.py` 在镜像的构建阶段汇总编进程序的依赖（Boost、simdjson、tl::expected）的许可证全文，随二进制和镜像发布 | MIT 等许可证要求随副本附带许可证文本；按 `cmake/dependencies.json` 生成，升级依赖时不会遗漏 |
| 什么提交可以发布（评审后增加） | 只发布已经合并到 main 的提交；tag 必须等于程序自报的版本 | 防止从未经 CI 的分支发布，防止版本号不一致 |
| 观测面的监听地址（评审后增加） | 本任务不改；SECURITY.md 写明检查只覆盖数据面，路线图 2.8 增加“`/metrics` 上线前扩展检查” | 观测面现在只有 `/health`、`/ready`；镜像中必须监听 0.0.0.0 才能做健康检查 |

## 收获与教训

- 陌生人视角的审查很有效：我写文档时知道“v0.2”指里程碑而不是程序版本、知道观测面只有健康检查，读者不知道。**文档的每一句状态描述都要能从仓库里验证**
- `workflow_dispatch` 可以在 tag 上运行，“手动运行只构建”不能只看 `github.ref`，要看 `github.event_name`
- 发布物要带第三方许可证，这一点任务设计没有想到；用依赖清单生成，避免手工维护
