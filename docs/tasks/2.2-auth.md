## 1. 目标与范围

**一句话：** 第一个内置插件 `auth`：客户端用 `Authorization: Bearer <网关 key>` 访问，网关只保存 key 的哈希，校验用常量时间比较；`llmgw keygen` 生成 key 和哈希。路线图的完成标准：**配置中不出现明文 key**。

| 做 | 不做 |
|---|---|
| 配置 `keys[]`：`id`、`hash`（`sha256:<64 位十六进制>`）；写了明文 key 时报错并说明怎么做 | `keys[].limits`（2.3）、`keys[].budget`（2.4）：出现时报“尚未支持” |
| `auth` 插件：校验 Bearer token，写 `ctx->auth.key_id`；失败返回 401 `invalid_api_key` | 按 key 区分可用的模型（以后） |
| 鉴权失败限速：同一个客户端地址失败太多次后返回 429，并减少日志 | 信任 `X-Forwarded-For`（没有可信代理的配置之前不能信） |
| `llmgw keygen --id <id>` | `llmgw reload`（3.1、3.4）；吊销只能改配置后重启 |
| `/v1/models` 也经过中间件链（2.1 留下的决定） | |
| 启用了 `auth` 时，`serve` 监听非本机地址不再需要 `--allow-unauthenticated` | |

## 2. 在架构中的位置

- `middleware`：`auth.cpp`（插件）、`include/llmgw/middleware/auth.h`（生成 key、计算哈希，供 keygen 使用）；链接 OpenSSL::Crypto（已经是 upstream 的依赖，**不新增第三方依赖**）
- `config`：`keys[]` 部分
- `core`：`RequestInfo` 增加 `bearer_token`、`client_address`、`kind`（写入者：Session）
- `server`：Session 填这三个字段；`/v1/models` 经过链
- `app`：注册 `auth`；`keygen` 命令；`keys` 与 `pipeline` 的交叉检查；启动时的监听检查
- 模块依赖不变

## 3. 接口设计

```cpp
// core/request_context.h —— RequestInfo 增加（写入者：Session）
enum class Endpoint : std::uint8_t { kChatCompletions, kListModels };
Endpoint endpoint = Endpoint::kChatCompletions;  ///< 插件据此决定是否计数、计费
std::string bearer_token;    ///< Authorization: Bearer 之后的部分（没有时为空）。不能写进日志
std::string client_address;  ///< 对端 IP（TCP 连接的地址；不看 X-Forwarded-For）

// config/snapshot.h
struct KeyConfig { std::string id; std::string hash; };  // hash = "sha256:" + 64 位小写十六进制
std::vector<KeyConfig> keys;

// middleware/auth.h
std::string generate_key();                   ///< "sk-gw-" + 43 个字符（32 字节随机数的 base64url），OpenSSL RAND_bytes
std::string hash_key(std::string_view key);   ///< "sha256:" + 十六进制
std::unique_ptr<MiddlewareFactory> make_auth_factory();
```

**配置示例：**

```json
"pipeline": ["auth"],
"keys": [ { "id": "app-chatbot", "hash": "sha256:9f2c…" } ]
```

## 4. 数据与状态

| 数据 | 归属 | 说明 |
|---|---|---|
| 哈希 → key_id 的表 | 每个 Worker 的 auth 实例（create 时从快照建立） | 只读；哈希的 32 字节作为键 |
| 鉴权失败计数（按客户端地址） | 每个 Worker 的 auth 实例 | 最多 4096 个地址；满了先清掉过期的，仍然满就不再记录新地址（只是不限速，不影响鉴权本身） |

## 5. 关键流程

`on_request`：
1. 没有 Bearer token → 记一次失败 → 401（`WWW-Authenticate: Bearer`）
2. `h = SHA-256(token)`；查表；用 `CRYPTO_memcmp` 比较 32 字节（常量时间）
3. 找到 → `ctx->auth.key_id = id`，放行。**有效的 key 永远不受限速影响**（先校验、后限速：同一个出口地址后面的正常应用不会被别人的错误拖累）
4. 没找到 → 这个地址的失败计数加一；1 分钟内超过 20 次 → 429 `rate_limited`（`Retry-After`），否则 401

`on_complete`：什么都不做（鉴权没有需要释放的资源）。

## 6. 失败与边界情况

| 情况 | 处理 |
|---|---|
| `Authorization` 不是 Bearer、多个 `Authorization` 头、token 前后有空格 | 不是 `Bearer <token>`（大小写不敏感）：当作没有 key；多个头：取第一个（Beast 的行为），与只有一个时等价 |
| 配置的 `hash` 写成了 key 本身（`sk-gw-…`）或写了 `key` 字段 | 配置错误：“这是 key 本身，配置中只能写哈希；用 llmgw keygen 生成”。**不能在错误信息里回显这个值** |
| 两个 id 的哈希相同 | 配置错误（同一个 key 对应两个身份） |
| `pipeline` 中有 `auth` 但 `keys` 为空 | 配置错误：所有请求都会被拒绝 |
| `keys` 不为空但 `pipeline` 中没有 `auth` | 警告：配置了 key 但不会校验 |
| 时序攻击 | 比较的是 SHA-256 的结果：哈希表查找的耗时只与哈希值有关，攻击者无法由此逼近一个 key；找到之后再用 `CRYPTO_memcmp` 比较全部 32 字节 |
| 为什么用 SHA-256 而不是 bcrypt / Argon2 | 慢哈希保护的是**低熵的口令**；网关 key 是 256 位随机数，没有字典可查，快速哈希就够了，而且每个请求都要算（慢哈希会让每个请求多花几十毫秒）。design.md 原来写的是 BLAKE3：SHA-256 由已有的 OpenSSL 提供，不新增依赖 |
| 日志 | 只记录 key_id 和客户端地址，**从不记录 token**；被限速的地址每分钟只记一行汇总 |
| `/v1/models` 被拒绝 | 与聊天接口相同（401 / 429） |

## 8. 风险与备选方案

| 问题 | 选择 | 备选与理由 |
|---|---|---|
| 鉴权失败限速怎么做 | 先校验、后限速：只对**失败**计数，超过阈值后失败返回 429 | 超过阈值后直接拒绝这个地址的所有请求：同一个出口地址（NAT、负载均衡器）后面的正常应用会被一个配错的客户端拖累。key 是 256 位随机数，限速的目的不是防暴力破解（本来就不可能），而是让配错的客户端退避、限制失败日志的量 |
| 按什么计数 | IPv4 按地址，IPv6 按 /64 | 一个 IPv6 用户通常有整个 /64，按地址计数等于没有限速 |
| 每个 Worker 一份计数 | 是（不加锁） | 实际阈值是 Worker 数 × 20；要精确限速需要跨线程共享，代价不值得 |
| token 放进 RequestContext | 是（`bearer_token`），注明不能记录 | 把全部请求头放进上下文：每个请求多复制一份请求头 |

## 收获与教训

- **第三方库的错误信息也是输出**：配置加载一直把 nlohmann 的说明原样转给用户，里面带着出错位置附近的原文。“不回显密钥”的检查只做在自己写的错误信息上是不够的
- 限速这类按客户端区分的逻辑，单元测试中手工填的地址证明不了 Session 真的把地址传进来了，要用真实的源地址端到端地测
- 性能对比中“与流数无关的固定差值”指向初始化成本，而不是热路径；单独测一次就能确认
- 已知限制：请求体在鉴权之前读完并解析（见 usage.md）；鉴权失败的计数每个 Worker 一份
